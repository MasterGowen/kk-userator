# 🔍 Code Review Guidelines — Руководство по код-ревью

**Источники:** [GitLab Code Review Guidelines](https://docs.gitlab.com/development/code_review/), [GitHub Docs — Helping others review your changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/getting-started/helping-others-review-your-changes)

---

## 📋 Обзор

**Код-ревью** — это процесс проверки изменений кода другими разработчиками перед слиянием в основную ветку.

**Цели:**
- ✅ Повышение качества кода
- ✅ Обмен знаниями в команде
- ✅ Раннее обнаружение багов
- ✅ Поддержание стандартов кода
- ✅ Обучение и менторство

---

## 🔄 Процесс ревью

```
┌─────────────────────────────────────────────────────────────────┐
│                    Code Review Process                          │
└─────────────────────────────────────────────────────────────────┘

  Author                          Reviewer
    │                               │
    │  [1] Создать PR               │
    │──────────────────────────────►│
    │                               │
    │                               │ [2] Проверить изменения
    │                               │
    │                               │ [3] Оставить комментарии
    │◄──────────────────────────────│
    │                               │
    │  [4a] Внести исправления      │
    │──────────────────────────────►│
    │                               │
    │                               │ [5] Проверить исправления
    │◄──────────────────────────────│
    │                               │
    │                               │ [6] Approve
    │──────────────────────────────►│
    │                               │
    │  [7] Мерж                     │
    │                               │
```

## 👤 Для автора PR

### Перед созданием PR

**Чеклист:**
```markdown
## Код
- [ ] Код следует соглашениям проекта
- [ ] Нет отладочного кода (print, debugger)
- [ ] Обработка ошибок добавлена
- [ ] Логирование на нужном уровне
- [ ] Нет хардкода (конфиги, env variables)

## Тесты
- [ ] Тесты написаны для новых функций
- [ ] Все тесты проходят локально
- [ ] Code coverage не уменьшился

## Документация
- [ ] README обновлён (если нужно)
- [ ] Комментарии в коде добавлены
- [ ] Changelog обновлён
```

### Создание PR

**Хорошее описание PR:**
```markdown
## Что сделано
Добавлена функция генерации паролей для пользователей Keycloak.

## Зачем
Требуется для задачи #123 — создание 200 учётных записей.

## Как тестировать
1. Запустить скрипт: python keycloak_user_generator.py --dry-run
2. Проверить output/credentials_*.csv
3. Убедиться, что пароли соответствуют требованиям

## Чеклист
- [x] Код отформатирован (black)
- [x] Тесты проходят (pytest)
- [x] Документация обновлена
```

**Размер PR:**
- ✅ Идеально: < 200 строк изменений
- ⚠️ Приемлемо: 200-400 строк
- ❌ Слишком большой: > 400 строк (разделить)

### Ответ на комментарии

**Правила:**
- ✅ Ответь на **каждый** комментарий
- ✅ Будь вежлив и конструктивен
- ✅ Если не согласен — объясни почему
- ✅ Внеси исправления или поясни решение

**Примеры ответов:**
```
✅ "Спасибо, исправлю в следующем коммите"
✅ "Хорошее замечание, но здесь это намеренно потому что..."
✅ "Согласен, изменю на более читаемый вариант"
❌ (игнорирование комментария)
```

## 👁️ Для ревьюера

### Обязанности ревьюера

**Что проверять:**
```markdown
## Функциональность
- [ ] Код делает то, что заявлено в описании
- [ ] Логика корректна
- [ ] Краевые случаи обработаны
- [ ] Нет регрессий

## Качество кода
- [ ] Код читаем и понятен
- [ ] Нет дублирования
- [ ] Функции/классы имеют одну ответственность
- [ ] Имена переменных/функций понятны

## Безопасность
- [ ] Нет уязвимостей (инъекции, XSS, CSRF)
- [ ] Валидация входных данных
- [ ] Нет секретов в коде (пароли, ключи)
- [ ] Авторизация/аутентификация проверена

## Производительность
- [ ] Нет очевидных узких мест
- [ ] Запросы к БД оптимизированы
- [ ] Нет утечек памяти

## Тесты
- [ ] Тесты покрывают новую функциональность
- [ ] Тесты читаемы и поддерживаемы
- [ ] Нет флакки-тестов
```

### Типы комментариев

**1. Блокирующие (Blockers)**
```
❌ "Это критичная уязвимость безопасности — нужно исправить до мержа"
❌ "Логика неверна, функция не работает как задумано"
```

**2. Рекомендации (Suggestions)**
```
⚠️ "Рекомендую вынести эту логику в отдельную функцию для читаемости"
⚠️ "Можно использовать list comprehension для упрощения"
```

**3. Вопросы (Questions)**
```
❓ "Почему выбрано это значение таймаута?"
❓ "Есть ли причина не использовать существующий метод?"
```

**4. Похвала (Praise)**
```
✅ "Отличное решение проблемы с гонкой данных!"
✅ "Красивый и читаемый код, спасибо!"
```

### Статусы ревью

| Статус | Значение | Когда использовать |
|--------|----------|-------------------|
| **Approve** | Одобрено | Все замечания исправлены, код готов к мержу |
| **Request Changes** | Требуются изменения | Есть блокирующие замечания |
| **Comment** | Комментарий | Есть вопросы/рекомендации, но не блокирует |

## ⏱️ Тайминги

### Для автора
- **Создание PR:** В тот же день, когда закончена работа
- **Ответ на комментарии:** В течение 24 часов
- **Исправления:** В течение 1-2 дней

### Для ревьюера
- **Первое ревью:** В течение 24 часов
- **Повторное ревью:** В течение 12 часов
- **Сложные PR:** Максимум 48 часов

## 🚫 Частые ошибки

### Ошибки автора
| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Огромный PR (>1000 строк) | Долгое ревью, пропуск багов | Делить на логические части |
| Нет описания PR | Ревьюер не понимает контекст | Писать подробное описание |
| Игнорирование комментариев | Конфликты, баги в коде | Отвечать на каждый комментарий |
| Защита своего кода | Токсичная атмосфера | Воспринимать критику конструктивно |

### Ошибки ревьюера
| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Поверхностное ревью | Баги проходят в код | Использовать чеклист |
| Токсичные комментарии | Конфликты в команде | Быть конструктивным |
| Затягивание ревью | Блокировка работы | Соблюдать тайминги |
| Микроменеджмент | Фрустрация автора | Фокусироваться на важном |

## 🛠️ Инструменты

### GitHub
- **Pull Requests** — основной инструмент
- **Code Owners** — автоматическое назначение ревьюеров
- **Required Reviews** — обязательное одобрение перед мержем
- **Suggestions** — предложение изменений прямо в комментарии

### GitLab
- **Merge Requests** — аналог PR
- **CODEOWNERS** — автоматическое назначение
- **Approvals** — требование одобрений
- **Diff view** — просмотр изменений

### Сторонние
- **Reviewable** — улучшенный интерфейс для ревью
- **Gerrit** — код-ревью для Git
- **Phabricator** — платформа для ревью

## 📊 Метрики

|---------|------|
| Время до первого ревью | < 24 часов |
| Время до мержа | < 48 часов |
| Количество комментариев на PR | 5-15 |
| Процент PR с блокирующими замечаниями | < 20% |
| Удовлетворённость процессом | > 80% |

## 🎯 Лучшие практики

### Для всех
1. **Будь вежлив** — критикуй код, не автора
2. **Будь конструктивен** — предлагай решения, а не только проблемы
3. **Будь своевременен** — соблюдай тайминги
4. **Учись** — ревью это возможность научиться новому

### Для автора
1. **Само-ревью** — проверь свой код перед отправкой
2. **Контекст** — дай ревьюеру всю необходимую информацию
3. **Открытость** — воспринимай замечания как помощь

### Для ревьюера
1. **Понимание** — убедись, что понял задачу
2. **Приоритеты** — фокусируйся на важном
3. **Баланс** — не требуй идеального кода, требуй рабочего
