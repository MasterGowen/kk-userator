## Роли

### Человек (User)

**Описание:** Заказчик, пользователь системы, стейкхолдер.

**Обязанности:**
- Формулирует задачи
- Утверждает артефакты на чекпоинтах
- Предоставляет доступы и контекст
- Принимает результат

**Точки взаимодействия:**
- Начало задачи
- Чекпоинты после каждого этапа
- Финальная приёмка

---

### Координатор (Coordinator)

**Описание:** Супервизор, управляющий командой субагентов.

**Обязанности:**
- Приём задачи от пользователя
- Ведение журнала активности (activity.log)
- Определение режима (Fast Path / Full Path / Orchestrator)
- Делегирование задач субагентам
- Контроль качества (через reviewer)
- Чекпоинты с пользователем

**Навыки:**
- Понимание контекста задачи
- Классификация задач
- Оркестрация агентов
- Журналирование

**Артефакты:**
- `docs/activity.log` — журнал активности

---

## Агенты

### Аналитик (Analyst)

**Описание:** Анализ требований и формализация задачи.

**Обязанности:**
- Анализ входных данных
- Выявление требований (явных и скрытых)
- Формализация ТЗ
- Выявление рисков

**Навыки:**
- Требовательный анализ
- Формализация
- Коммуникация (задавание вопросов)

**Артефакты:**
- `docs/requirements.md`

**Вход:** Описание задачи от пользователя
**Выход:** Структурированное ТЗ

---

### Архитектор (Architect)

**Описание:** Системный архитектор.

**Обязанности:**
- Проектирование архитектуры
- Выбор технологического стека
- Проектирование компонентов
- Спецификация API

**Навыки:**
- Системное мышление
- Знание паттернов
- Оценка компромиссов

**Артефакты:**
- `docs/architecture.md`
- `docs/adr-*.md` — архитектурные решения

**Вход:** `requirements.md`
**Выход:** Архитектурная спецификация

---

### Планировщик (Planner)

**Описание:** Планирование и трекинг работ.

**Обязанности:**
- Декомпозиция задачи
- Оценка трудоёмкости
- Приоритизация (MoSCoW)
- Трекинг прогресса

**Навыки:**
- Планирование
- Оценка рисков
- Управление зависимостями

**Артефакты:**
- `docs/plan.md`

**Вход:** `architecture.md` + `requirements.md`
**Выход:** План-график

---

### Инженер (Engineer)

**Описание:** Инженер-разработчик.

**Обязанности:**
- Реализация кода
- Написание тестов
- Документирование кода
- Git-коммиты

**Навыки:**
- Программирование
- Тестирование
- Git workflow

**Артефакты:**
- `src/` — исходный код
- `tests/` — тесты
- `requirements.txt` — зависимости

**Вход:** `architecture.md` + `requirements.md`
**Выход:** Рабочий код

---

### Ревьюер (Reviewer)

**Описание:** Технический ревьюер / Критик.

**Обязанности:**
- Проверка артефактов
- Выявление проблем
- Оценка рисков
- Предложение улучшений

**Навыки:**
- Критическое мышление
- Внимание к деталям
- Конструктивная критика

**Артефакты:**
- `reviews/<этап>-<дата>.md`

**Вход:** Любой артефакт
**Выход:** Отчёт о ревью

---

### Документатор (Documenter)

**Описание:** Технический писатель.

**Обязанности:**
- Создание документации
- Ведение changelog
- Поддержка актуальности

**Навыки:**
- Техническое письмо
- Структурирование информации
- Внимание к деталям

**Артефакты:**
- `README.md`
- `docs/changelog.md`
- `docs/*.md`

**Вход:** Все артефакты
**Выход:** Документация

## Взаимодействия

### Full Path (крупные задачи)

```
User → Coordinator → Analyst → Reviewer → Architect → Reviewer → Planner → Engineer → Reviewer → Done
                              ↑                                                      ↓
                              └────────────── Documenter ───────────────────────────┘
```

### Fast Path (мелкие задачи <2ч)

```
User → Coordinator → Engineer → Reviewer → Done
                         ↓
                   Documenter
```

### Orchestrator (>3 итераций)

```
User → Coordinator → Orchestrator → [Sub-task 1 → Analyst → Architect → Engineer]
                                    [Sub-task 2 → Analyst → Architect → Engineer]
                                    [Sub-task 3 → Analyst → Architect → Engineer]
                                    ↓
                              Synthesizer → Reviewer → Done
```

## Матрица ответственности (RACI)

| Этап | User | Coordinator | Analyst | Architect | Engineer | Reviewer | Documenter |
|------|------|-------------|---------|-----------|----------|----------|------------|
| Анализ | C | A | R | I | I | I | I |
| Архитектура | C | A | C | R | I | R | I |
| Планирование | I | A | C | C | C | R | I |
| Реализация | I | A | I | C | R | R | I |
| Документирование | I | I | I | I | C | I | R |
| Приёмка | R | A | I | I | I | C | I |

**RACI:**
- **R**esponsible — исполняет
- **A**ccountable — отвечает (один человек)
- **C**onsulted — консультирует
- **I**nformed — информируется

# 🤖 Multi-Agent Patterns — Паттерны мульти-агентных систем

**Источник:** [Six Core Design Principles for Multi-AI Agent Systems](https://cobusgreyling.substack.com/p/six-core-design-principles-for-multi)

---

## 📋 Обзор

Шесть основных паттернов проектирования для мульти-агентных систем на базе LLM:

1. **Flow Control** — Управление потоком
2. **Interaction Styles** — Стили взаимодействия
3. **History Sharing** — Обмен историей
4. **Network Configurations** — Конфигурации сети
5. **Human Interaction** — Взаимодействие с человеком
6. **ReAct Workflow** — Рабочий процесс агента

---

## 1. Flow Control — Управление потоком

### Варианты

| Тип | Описание | Когда использовать |
|-----|----------|-------------------|
| **Явный (Explicit)** | Предопределённые последовательности, графы, оркестрируемые рабочие процессы | Когда требуется предсказуемость и аудит |
| **Динамический (LLM-driven)** | Решения принимаются LLM во время выполнения | Когда нужна гибкость и адаптивность |

### Пример: Явный поток (kk-userator)

```
User → Coordinator → Analyst → Reviewer → Architect → Reviewer → Engineer → Reviewer → Done
```

**Преимущества:**
- ✅ Предсказуемость
- ✅ Легче отладка
- ✅ Явные точки контроля

**Недостатки:**
- ❌ Меньше гибкости
- ❌ Не адаптируется к сложным сценариям

### Пример: Динамический поток

```
User → [LLM решает] → Analyst или Engineer → [LLM решает] → ...
```

**Преимущества:**
- ✅ Адаптивность
- ✅ Пропускает ненужные этапы

**Недостатки:**
- ❌ Стохастическое поведение
- ❌ Сложнее отладка

---

## 2. Interaction Styles — Стили взаимодействия

### Handoff (Передача промптов)

```
Agent A → [передаёт контекст] → Agent B → [передаёт контекст] → Agent C
```

**Когда использовать:**
- Простые цепочки задач
- Агенты работают последовательно
- Минимум инструментов

### Tool Flow / Function Calling

```
                    ┌──────────────┐
                    │  Coordinator │
                    └──────┬───────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
         ▼                 ▼                 ▼
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ Analyst  │    │ Engineer │    │ Reviewer │
   └──────────┘    └──────────┘    └──────────┘
```

**Когда использовать:**
- Сложные системы с инструментами
- Параллельное выполнение
- Координация через супервизора

---

## 3. History Sharing — Обмен историей

### Полный трассировочный след

```
Agent A: [Thought, Action, Observation] → Agent B: [Thought, Action, Observation]
              │                                    │
              └───────────> Shared Log <───────────┘
```

**Когда использовать:**
- Отладка и аудит
- Обучение агентов
- Комплаенс требования

**Преимущества:**
- ✅ Полная прозрачность
- ✅ Легче найти ошибку

**Недостатки:**
- ❌ Большой расход токенов
- ❌ Медленнее работа

### Только финальные результаты

```
Agent A: [Result] → Agent B: [Result]
```

**Когда использовать:**
- Эффективность важнее прозрачности
- Приватность внутренних шагов
- Ограниченный контекст

---

## 4. Network Configurations — Конфигурации сети агентов

### Супервизор (Supervisor)

```
              ┌─────────────┐
              │ Supervisor  │
              └──────┬──────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ Leaf 1 │  │ Leaf 2 │  │ Leaf 3 │
   └────────┘  └────────┘  └────────┘
```

**kk-userator использует эту конфигурацию**

**Когда использовать:**
- Чёткое разделение ответственности
- Централизованная координация
- Иерархическая структура

### Рой (Swarm)

```
   ┌──────┐    ┌──────┐
   │ A1   │◄──►│ A2   │
   └──┬───┘    └──┬───┘
      │           │
      └─────┬─────┘
            │
         ┌──────┐
         │ A3   │
         └──────┘
```

**Когда использовать:**
- Децентрализованное принятие решений
- Агенты равноправны
- Handoffs между агентами

### Иерархическая

```
         ┌──────────────┐
         │ Top Manager  │
         └──────┬───────┘
                │
        ┌───────┴───────┐
        │               │
   ┌────▼────┐    ┌────▼────┐
   │ Manager │    │ Manager │
   └────┬────┘    └────┬────┘
        │               │
   ┌────┴────┐    ┌────┴────┐
   │Leaf │Leaf│    │Leaf │Leaf│
   └─────┴─────┘    └─────┴─────┘
```

**Когда использовать:**
- Сложные организации
- Много уровней абстракции
- Масштабирование

### Единая информационная среда (SIE)

```
   ┌──────┐     ┌──────┐
   │ A1   │     │ A2   │
   └──┬───┘     └──┬───┘
      │            │
      └─────┬──────┘
            │
      ┌─────▼─────┐
      │   SIE     │
      │  (Router) │
      └─────┬─────┘
            │
      ┌─────▼─────┐
      │   A3      │
      └───────────┘
```

**Когда использовать:**
- Разнородные источники данных
- Динамическая маршрутизация
- Общие данные между агентами

---

## 5. Human Interaction — Взаимодействие с человеком

### Human-in-the-loop

```
Agent → [Решение] → Human → [Approve/Reject] → Agent
```

**Когда использовать:**
- Критические решения
- Высокие риски
- Юридические требования

**Пример в kk-userator:**
- Чекпоинты после каждого этапа
- Пользователь утверждает перед переходом к следующему этапу

### Human-on-the-loop

```
Agent → [Действие] → Human → [Monitor only]
```

**Когда использовать:**
- Низкие риски
- Автоматизация рутинных задач
- Надзор без вмешательства

---

## 6. ReAct Workflow — Рабочий процесс агента

### Цикл ReAct

```
┌─────────────────────────────────────────────┐
│            ReAct Agent Loop                 │
└─────────────────────────────────────────────┘

     ┌─────────┐
     │ Thought │  (Что я знаю? Что нужно сделать?)
     └────┬────┘
          │
          ▼
     ┌─────────┐
     │ Action  │  (Вызов инструмента, API, функции)
     └────┬────┘
          │
          ▼
     ┌─────────────┐
     │ Observation │  (Результат действия)
     └────┬────────┘
          │
          ▼
     [Повторить или Завершить]
```

**Пример:**

```
Thought: Мне нужно создать пользователей в Keycloak.
         Сначала проверю доступность API.

Action: keycloak_admin.get_version()

Observation: {"version": "23.0.1"}

Thought: API доступно. Теперь создам группу.

Action: keycloak_admin.create_group({"name": "engforinclusb-users"})

Observation: {"id": "abc123", "name": "engforinclusb-users"}

Thought: Группа создана. Теперь создам пользователей.
...
```

**Когда использовать:**
- Индивидуальные агенты
- Задачи с инструментами
- Итеративное решение проблем

## 📊 Сравнение конфигураций

| Конфигурация | Сложность | Масштабируемость | Гибкость | Отладка |
|--------------|-----------|------------------|----------|---------|
| Супервизор | Низкая | Средняя | Низкая | Легко |
| Рой | Средняя | Высокая | Высокая | Сложно |
| Иерархическая | Высокая | Высокая | Средняя | Сложно |
| SIE | Высокая | Очень высокая | Очень высокая | Очень сложно |

## 🎯 Применение в kk-userator

| Паттерн | Текущая реализация | Потенциальные улучшения |
|---------|-------------------|------------------------|
| **Flow Control** | Явный (Coordinator управляет) | Добавить динамический для простых задач |
| **Interaction** | Tool Flow (супервизор + листовые агенты) | ✅ Оптимально |
| **History** | Полный след (activity.log) | ✅ Оптимально с маркировкой доверия |
| **Network** | Супервизор | Рассмотреть SIE для масштабирования |
| **Human** | In-the-loop (чекпоинты) | ✅ Оптимально для критичных задач |
| **ReAct** | Встроен в агентов | ✅ Оптимально |

## Координатор (Coordinator)

**Текущая версия:** 1.1 (2026-03-19)

**Роль:** Управление командой специализированных субагентов для эффективной реализации проекта.

**Обязанности:**
1. Принимать задачу от пользователя
2. **Вести журнал активности (activity.log) с метками времени**
3. Определять, какой субагент нужен на текущем этапе
4. Делегировать задачу соответствующему субагенту
5. Контролировать качество результата
6. Передавать результат следующему субагенту или пользователю

**Принцип журналирования:**
> Лог — это не «отдельное действие», а ПЕРВАЯ ЧАСТЬ генерации ответа.

**Порядок генерации:**
1. Получить сообщение пользователя → обновить контекст
2. Сгенерировать запись в лог (метка времени + цитата пользователя)
3. Сгенерировать обработку и ответ
4. Лог и ответ — это ЕДИНЫЙ поток токенов

**Формат записи в лог:**
```
[YYYY-MM-DD HH:MM:SS] [TRUSTED/UNTRUSTED] <ТИП> <СУБЪЕКТ>: <описание>
```

**Режимы работы:**
- 🚀 **Fast Path** — для мелких задач <2 часов
- 🏗️ **Full Path** — для крупных задач
- 🎼 **Orchestrator** — для задач >3 итераций

**История версий:**
| Версия | Дата | Изменения |
|--------|------|-----------|
| 1.0 | 2026-03-18 | Базовая версия |
| 1.1 | 2026-03-19 | Добавлено журналирование с маркировкой доверия |

## Аналитик (Analyst)

**Текущая версия:** 1.0 (2026-03-18)

**Роль:** Анализ требований и формализация задачи

**Goal:** Проанализировать исходные требования и формализовать их в структурированное ТЗ

**Tasks:**
- Изучить входные данные от пользователя

- Сформулировать нефункциональные требования

**Output Format:**
- Краткое резюме задачи (2-3 предложения)
- Список функциональных требований (нумерованный)
- Список нефункциональных требований (нумерованный)
- Критерии приёмки (чеклист)
- Риски и допущения (таблица)
- Открытые вопросы к пользователю

**Артефакт:** `docs/requirements.md`

**Rules:**
- Задавай уточняющие вопросы, если требования размыты
- Не предполагай — спрашивай
- Фокусируйся на ЧТО, а не на КАК

**Dependencies:**
- Любой артефакт для ревью

**Tasks:**
- Проверить соответствие требованиям
- Выявить логические противоречия
- Найти узкие места
- Оценить риски безопасности
- Проверить на полноту
- Предложить улучшения
- **Проверить зависимости (requirements.txt) на соответствие коду**
- **Проверить импорты в коде на наличие в зависимостях**

**Output Format:**
- Статус (зелёный/жёлтый/красный)
- Проблемы по приоритетам (критично/важно/рекомендация)
- Рекомендации по исправлению

- Если найдена проблема — сначала запроси уточнение у engineer
- Дай engineer возможность исправить или объяснить перед финальным вердиктом
- Максимум 3 итерации уточнений перед вынесением статуса

# 🌿 Git Workflow — GitHub Flow

**Источник:** [GitHub Docs — About branches](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-branches)

---

## 📋 Обзор

**GitHub Flow** — это легковесный, ветка-ориентированный воркфлоу, разработанный для непрерывной доставки и частых развёртываний.

**Ключевые принципы:**
- ✅ Ветки изолируют изменения
- ✅ Короткоживущие feature-ветки
- ✅ Pull Request как точка ревью
- ✅ Мерж после одобрения
- ✅ Удаление ветки после мержа

---

## 🔄 Рабочий процесс

```
┌─────────────────────────────────────────────────────────────────┐
│                        GitHub Flow                              │
└─────────────────────────────────────────────────────────────────┘

     main (production-ready)
       │
       ├──────────────────────────────────────────────────────┐
       │                                                      │
       ▼                                                      │
  [1] Создать ветку                                           │
       │                                                      │
       ▼                                                      │
  [2] Делать коммиты                                          │
       │                                                      │
       ▼                                                      │
  [3] Открыть Pull Request                                    │
       │                                                      │
       ▼                                                      │
  [4] Code Review                                             │
       │                                                      │
       ├─────► [5a] Замечания ─────► Исправить ─────┐         │
       │                                            │         │
       ▼                                            │         │
  [5b] Одобрено                                     │         │
       │                                            │         │
       ▼                                            │         │
  [6] Мерж в main                                   │         │
       │                                            │         │
       ▼                                            │         │
  [7] Удалить ветку ◄───────────────────────────────┘         │
                                                              │
└──────────────────────────────────────────────────────────────┘
```

---

## 📝 Этапы подробно

### 1. Создать ветку

```bash
git checkout main
git pull origin main
git checkout -b feature/short-description
```

**Соглашения об именовании:**
| Префикс | Назначение | Пример |
|---------|------------|--------|
| `feature/` | Новая функциональность | `feature/user-auth` |
| `fix/` | Исправление бага | `fix/login-error` |
| `docs/` | Обновление документации | `docs/readme-update` |
| `refactor/` | Рефакторинг | `refactor/auth-module` |
| `test/` | Добавление тестов | `test/user-api` |
| `chore/` | Вспомогательные изменения | `chore/update-deps` |

**Правила:**
- Используйте `kebab-case` (через дефис)
- Краткое описание (2-4 слова)
- Избегайте специальных символов

---

### 2. Делать коммиты

```bash
git add .
git commit -m "type: описание"
git push origin feature/short-description
```

**Соглашения коммитов (Conventional Commits):**
```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

| Type | Назначение |
|------|------------|
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `docs` | Документация |
| `style` | Форматирование |
| `refactor` | Рефакторинг |
| `test` | Тесты |
| `chore` | Вспомогательное |

**Пример:**
```
feat(auth): добавить OAuth2 авторизацию

- Интеграция с Google OAuth
- Обработка токенов
- Обновление README

Closes #123
```

---

### 3. Открыть Pull Request

**Создание PR:**
```bash
# Через GitHub CLI
gh pr create --title "feat: добавить OAuth2" --body "Описание изменений"

# Или через GitHub UI: github.com/<owner>/<repo>/pull/new/branch
```

**Шаблон описания PR:**
```markdown
## Что сделано
- [ ] Описание изменений

## Зачем
- [ ] Проблема/задача

## Как тестировать
- [ ] Шаги для проверки

## Чеклист
- [ ] Код отформатирован
- [ ] Тесты проходят
- [ ] Документация обновлена
```

---

### 4. Code Review

**Для автора PR:**
- ✅ Запроси ревью явно (@reviewer)
- ✅ Ответь на все комментарии
- ✅ Внеси исправления до мержа
- ✅ Обновляй PR по замечаниям

**Для ревьюера:**
- ✅ Проверь соответствие требованиям
- ✅ Оставь конструктивные комментарии
- ✅ Используй [Approve / Request Changes / Comment]
- ✅ Проверь тесты и документацию

**Чеклист ревью:**
```markdown
## Код
- [ ] Логика корректна
- [ ] Нет дублирования
- [ ] Обработка ошибок
- [ ] Тесты покрывают изменения

## Безопасность
- [ ] Нет уязвимостей
- [ ] Валидация входных данных
- [ ] Нет секретов в коде

## Документация
- [ ] README обновлён
- [ ] Комментарии в коде
- [ ] Changelog обновлён
```

---

### 5. Мерж

**Требования перед мержем:**
- ✅ Все статус-чеки пройдены (CI/CD)
- ✅ Получено одобрение (1+ reviewer)
- ✅ Нет конфликтов слияния
- ✅ Чеклист ревью заполнен

**Способы мержа:**
| Метод | Когда использовать |
|-------|-------------------|
| **Squash and merge** | Feature-ветка с множеством коммитов |
| **Merge commit** | Сохранить историю ветки |
| **Rebase and merge** | Линейная история (для мелких изменений) |

**После мержа:**
```bash
git checkout main
git pull origin main
git branch -d feature/short-description  # Удалить локальную
git push origin --delete feature/short-description  # Удалить удалённую
```

---

### 6. Удаление ветки

**Важно:**
- ❌ Нельзя удалить ветку с открытым PR
- ✅ GitHub предлагает удалить после мержа
- ✅ Зависимые PR автоматически обновляются

---

## 🛡️ Защищённые ветки (Protected Branches)

**Настройки защиты для `main`:**
```
✅ Require a pull request before merging
✅ Require approvals (1 reviewer minimum)
✅ Require status checks to pass before merging
✅ Require branches to be up to date before merging
✅ Include administrators (применяется ко всем)
```

**Дополнительно:**
- ✅ Require signed commits
- ✅ Require linear history
- ✅ Allow force pushes (только для администраторов)
- ✅ Allow deletions (не рекомендуется для main)

---

## 📊 Метрики воркфлоу

| Метрика | Цель |
|---------|------|
| Время жизни ветки | < 3 дней |
| Время ревью | < 24 часов |
| Размер PR | < 400 строк изменений |
| Количество коммитов в PR | 1-10 (после squash) |
| Конфликты слияния | < 5% PR |

---

## ⚠️ Частые ошибки

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Долгоживущие ветки (>1 недели) | Конфликты, устаревание | Дробить на мелкие PR |
| Огромные PR (>1000 строк) | Долгое ревью, пропуск багов | Делить на логические части |
| Мерж без ревью | Баги в production | Включить защиту ветки |
| Force push в shared branch | Потеря коммитов коллег | Запретить force push |
| Игнорирование CI | Непрошедшие тесты | Требовать статус-чеки |
